You are reviewing one change in a git repository. The repository is at:

{{REPO_PATH}}

The change under review is `{{DIFF_CMD}}`: everything this branch changes relative to its base. The base commit is `{{BASE}}`; read a file as it was there with `git show {{BASE}}:<path>`.{{UNTRACKED_NOTE}} Review it as a pull request you are seeing for the first time.

You are one of several reviewers working on this change in parallel. Each has a different focus, and the reports are merged afterwards. Your focus is: **conformance: regressions against the base, repository rules, documentation and copy, tests, wiring and compatibility**. Spend your effort there and go deep. If you notice a defect outside your focus, add one line for it under "Outside my focus" at the end; do not investigate it.

Ground rules:
- Work only from the files in that directory. Do not use the network, GitHub or `gh`, and do not read earlier reviews, review comments or other branches. The review must come from the code.
- Do not modify, commit or delete anything in the repository. You may run read-only commands, and you may run existing tests or scripts if they work without installing anything.
- Save the complete review to `{{OUT}}`. That is the only file you may write. Then reply with only the word `saved`. Write the review for someone who will fix what you report without asking you questions.

The goal is a review that does not need a second round. Past reviews of this kind of work failed in a specific way: the reviewer reported one instance of a problem, the author fixed that one line, and the next round found the sibling site or the bug the fix created. Work so that does not happen.

## How to work

1. Settle context. Settle context. Read the repo rule files (AGENTS.md, CLAUDE.md, README, any plan or design doc the change refers to). Note decided policies and repo rules the change must follow.

2. List what the change adds or alters that falls in your focus, then write a unit ledger: every function, handler, query, trigger, hook, component, script or document section in non-test source that your focus applies to, one line each. Every unit on the ledger gets every pass below that applies to it. Do not spend the review on the unit that looks most interesting and skim the rest. Put the ledger in your coverage statement with a mark for each unit you traced line by line.

3. Follow each item out of the diff. The diff is where to start, and the defect is often in a file it did not touch. For each inventory item open its counterpart: the server authorizer for a UI gate (and the reverse); every caller of a guarded operation; every producer and consumer of a limited or validated field; the real consumer's parser for any hand-rolled parse; proxy rules, cookie paths and E2E helpers for a moved route; registries and examples for an env var; every mapper that can see a new error; every reader and invalidation site of a cache key; every other path that locks the same rows; test helpers and fixtures for a changed UI flow; every other file that states a changed fact; vendor docs or pinned library source for third-party behavior.

4. Report the class, not the instance. When something is wrong at one site, name the invariant in one sentence, then enumerate every site that must uphold it: other verbs on the same resource, other flows of the same kind, other call sites, other transitions of the state machine, other backends, environments and platforms, other branches of the same component (success and failure), other error codes, other files stating the same fact, other input variants. Check each and list them in the finding.

5. State the inverse failure. For every guard, filter, fallback or tightening in the change, and for every fix you suggest, say who is hurt if it is too loose and who if it is too strict.

6. Verdicts. Every row of every table and every pass in this review ends in one of two verdicts: `finding`, or `holds` followed by the file and line that makes the invariant true. Do not write acceptable, fine, intended, by design, expected, defensible, tolerable or harmless as a verdict or as a reason not to report something. If what is displayed, what a client can do, what is stored or what a response says disagrees with what is actually true, even for a moment and even if a later action would correct it, the row is a finding at Low or higher. Deciding that the author meant it is not your job: report it, and say in one clause that it may be intentional.

7. Verify before reporting. For claims about library, runtime or vendor behavior, read the pinned source or docs in the repo. For "this is not handled", read the whole function and its callers first. For "this test will fail", run it if you can. Trace any fix you suggest for its own inverse failure, or state the constraint the fix must meet instead of prescribing code. Where the logic you are checking is a pure function and a runtime is already installed, run it on your concrete values with inline code on the command line (create no files) instead of tracing it by hand. Mark every table row and scenario `executed` or `read`.

## Passes for your focus

**Behavior compared with the base.** Compare behavior with the base. For every predicate, filter, guard, status check, default, limit and return value the change alters, write what the base commit returned for the same input and what the head returns. List every input that used to succeed and now fails, and every input that used to fail and now succeeds. Each one is either required by the stated purpose of the change or it is a regression to report as a finding. Put the table in your report: input, what the base returned, what the head returns, and whether the change is required by the stated purpose or is a regression.

**Rule audit.** Read every rule file in the repository (AGENTS.md, CLAUDE.md, CONTRIBUTING, lint and design-system docs, the plan the change implements). List every rule that can be checked by reading code: required tokens or helpers in place of literal values, forbidden APIs, suppressions and ignore pragmas, what may be logged, where paid or permission checks must read from, layering and import rules, migration policy, required tests or docs for a kind of change. Number them. For each rule, search every line the change adds for violations; do this mechanically with grep over the diff, not from memory of reading it. Put a table in your report: rule, where it is stated, how you searched, and the verdict. A violated repository rule is a finding even when the code works.

**Statements against code.** Every factual sentence the change adds or leaves standing in docs, plans, runbooks, comments, UI copy, error messages and test names is a claim. Check each against the code. When the change alters a fact, search every file that states it. A limit, status or behavior described in one place and different in the code or in another place is a finding. This pass has two parts, and each leaves its own table.
   Part one, the sentences the change writes. Go through the diff of every document, plan, runbook and copy file line by line (the change's diff restricted to those files, and the string tables), and through the comments the change adds in code. Start with the guarantees, because they are the sentences a reviewer skims past. Collect them mechanically: grep the added lines of that diff for `never|always|only|cannot|can't|must|exactly|every|no longer|nothing else`, give the command and the number of hits, and make every hit a row of a guarantees table; do not merge rows or drop a hit because another row looks similar. For each guarantee, checking the main path is not enough, so the guarantees table has one column per path: the main path; the same action retried, resumed or re-resolved after a failed attempt; the same action after a refresh, reload or replacement of the thing happened in between; every other entry point that reaches the same outcome. Each cell holds the `file:line` of the code that runs on that path and its own verdict, or `no such path` with what you searched for. In each cell compare by the full identity the sentence promises (source, version, provenance), not by ids alone: a lookup by ids that returns whatever now sits under them is a different thing from the one the guarantee is about. For a guarantee that is a static fact (a version number, a name, a file location), write `static` in the three other-path cells. The row is a `finding` if any cell is. Then list the remaining added or edited sentences that state what the system does, one row each. State the number of guarantee rows and the number of other sentences.
   Part two, statements elsewhere about what the change adds. Do not stop at the sentences the change edits, or at the section of a document that is about the feature. Write a search list in your report. Build it mechanically from the diff, not from the topics of the feature: one line for every source file the change adds (`git diff --diff-filter=A --name-only`), one for every component, screen, hook or type those files export, and one for every thing the change renames. For each line give the terms you searched: its identifier, its file name, and its name written as plain words, with each distinctive word also searched alone (for `ArchivedNote`: "archived note", "archived", so that "an archived note" and "the note, once archived" both match). Give the command you ran over every rule, design and plan document, and the number of hits per document. Every hit is a row of the statements table, wherever it sits: a row of a table of values, a list of examples and a caption are statements. Check each one against the line of code that actually decides it. Follow wrappers and composition down to the element that sets the property, because a new component that wraps an existing one shows whatever the inner one sets. Put both tables in your report, each with: the statement, where it is stated, the line of code that decides it (for a guarantee, one line per path checked), and the verdict.

**Tests.** For each test the change adds or alters: name the production change that would make it fail. If there is none, it is a finding. Look for tests that create the state production should create, fakes whose behavior differs from the real dependency, assertions that pass vacuously, ordering or timing dependence, global state not restored on failure, and helpers or fixtures left behind by a changed flow. List behaviors the change adds that no test would catch if they broke.

**Wiring.** For each new env var, route, method, script, flag, event type, capability or config key: find its consumer and every registry, example, schema, generated artifact and client that must know about it. For each renamed or removed thing: search for every remaining reference. For each new requirement on a dependency passed in (a method that must exist, a type that must be wider): check every caller and every declared type.

**Mixed versions.** Old client with new server, new client with old server, old rows with new code, a rollback after the change has written data. A newly required field, a narrowed type or an edited applied migration is a finding unless the change handles each of these.

**Checklist.** Tests: a test that cannot fail for the bug; tests that create state production should create; fakes with different semantics; ambient env and timing; global state not restored; vacuous assertions; helpers left behind by a UI change. Config, infrastructure and scripts: env vars without registry entries or validation; local and prod twins out of step; proxy routes that forward caller-controlled controls; hard-coded hosts; scripts without timeouts, cleanup or correct exit codes. Docs, plans and copy: every factual sentence checked against the code; a status changed in one place and not others. Runtime compatibility, wiring and quality gates: APIs missing on a target runtime; features wired on one screen only; new things with no consumer; suppressions added in the change.

## What to report and what not to

Report every defect you observe in the changed behavior, including small ones: rate it Low, but do not drop it. If you noticed something wrong and can state the scenario, it belongs in the findings, not in a coverage note. A stale message, a hint that outlives its truth, or an error that stays after success are defects.

Do not report style, naming, comment wording, micro-performance, or speculative "a future caller could" concerns. Defects in code the change only moved should be listed separately as pre-existing.

## Report format

For each finding:
- Title and severity (High, Medium, Low, rated by consequence).
- Invariant: the rule being broken, in one sentence.
- Sites: every violating location as `file:line`, and the sibling sites you checked and found fine.
- Scenario: concrete inputs and state leading to the wrong outcome.
- Reach: what produces the scenario's starting condition in the application as it stands today (the screen, action, caller or stored data), as `file:line`. If you find nothing that produces it today, write `no trigger found today: needs <what would have to exist>`. Keep the finding either way: this line is for whoever ranks the findings, and it is not a reason to drop or soften one.
- Fix constraint: what a correct fix must guarantee, and the inverse failure it must not create.
- Verification: reproduced, ran a test, read source, or inferred from reading.

Include every table the passes ask for.

After the tables, write a finding-row index. Give one line for every table row or cell whose verdict is `finding`: the table, the row (and column), the number of the written finding that covers it, and a quotation of the sentence in that finding that says what goes wrong at that row's own reader, site or input. A written finding about a different reader, site or path of the same value does not cover the row, even when the cause is shared. If you cannot quote such a sentence, write a new finding for the row before you finish. State the number of `finding` rows and cells in your tables and the number of index lines; the two must be equal.

End with a coverage statement: the unit ledger, the passes you ran and what you enumerated for each, anything you ran, and what you did not check and why. Then the "Outside my focus" list.
