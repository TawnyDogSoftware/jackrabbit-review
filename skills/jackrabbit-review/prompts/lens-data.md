- Do not modify, commit or delete anything in the repository. You may run read-only commands, and you may run existing tests or scripts if they work without installing anything.
- Save the complete review to `{{OUT}}`. That is the only file you may write. Then reply with only the word `saved`. Write the review for someone who will fix what you report without asking you questions.

The goal is a review that does not need a second round. Past reviews of this kind of work failed in a specific way: the reviewer reported one instance of a problem, the author fixed that one line, and the next round found the sibling site or the bug the fix created. Work so that does not happen.

## How to work

1. Settle context. Settle context. Read the repo rule files (AGENTS.md, CLAUDE.md, README, any plan or design doc the change refers to). Note decided policies and repo rules the change must follow.

2. List what the change adds or alters that falls in your focus, then write a unit ledger: every function, handler, query, trigger, hook, component, script or document section in non-test source that your focus applies to, one line each. Every unit on the ledger gets every pass below that applies to it. Do not spend the review on the unit that looks most interesting and skim the rest. Put the ledger in your coverage statement with a mark for each unit you traced line by line.

3. Follow each item out of the diff. The diff is where to start, and the defect is often in a file it did not touch. For each inventory item open its counterpart: the server authorizer for a UI gate (and the reverse); every caller of a guarded operation; every producer and consumer of a limited or validated field; the real consumer's parser for any hand-rolled parse; proxy rules, cookie paths and E2E helpers for a moved route; registries and examples for an env var; every mapper that can see a new error; every reader and invalidation site of a cache key; every other path that locks the same rows; test helpers and fixtures for a changed UI flow; every other file that states a changed fact; vendor docs or pinned library source for third-party behavior.

4. Report the class, not the instance. When something is wrong at one site, name the invariant in one sentence, then enumerate every site that must uphold it: other verbs on the same resource, other flows of the same kind, other call sites, other transitions of the state machine, other backends, environments and platforms, other branches of the same component (success and failure), other error codes, other files stating the same fact, other input variants. Check each and list them in the finding.

5. State the inverse failure. For every guard, filter, fallback or tightening in the change, and for every fix you suggest, say who is hurt if it is too loose and who if it is too strict.

6. Verdicts. Every row of every table and every pass in this review ends in one of two verdicts: `finding`, or `holds` followed by the file and line that makes the invariant true. Do not write acceptable, fine, intended, by design, expected, defensible, tolerable or harmless as a verdict or as a reason not to report something. If what is displayed, what a client can do, what is stored or what a response says disagrees with what is actually true, even for a moment and even if a later action would correct it, the row is a finding at Low or higher. Deciding that the author meant it is not your job: report it, and say in one clause that it may be intentional.

7. Verify before reporting. For claims about library, runtime or vendor behavior, read the pinned source or docs in the repo. For "this is not handled", read the whole function and its callers first. For "this test will fail", run it if you can. Trace any fix you suggest for its own inverse failure, or state the constraint the fix must meet instead of prescribing code. Where the logic you are checking is a pure function and a runtime is already installed, run it on your concrete values with inline code on the command line (create no files) instead of tracing it by hand. Mark every table row and scenario `executed` or `read`.

## Passes for your focus

**Multi-step writes and check-then-act.** Multi-step writes: two or more writes or a write plus a side effect not in one transaction; state left if the process dies between steps; whether a retry can complete; irreversible or destructive steps ordered before the step they depend on; files written in place. Check-then-act and locking: a read deciding a write without a constraint, conditional update or lock covering the whole invariant; state transitions without a precondition on current status; authority not re-checked inside the transaction; lock order, lock mode and lock-key canonical form; check-await-set on a cache; UI guarded only by a disabled prop.

**Retry.** A retry pass: for each operation that changes state, assume it committed and the response was lost, so the caller sends the same request again. Trace the second request through the changed code. It must end in the same success the first would have returned, not in not-found, conflict or a duplicate. Do the same for two identical requests arriving together.

**Guard placement.** A guard-placement pass: for each check of authority, ownership, currency, revocation, lease or staleness, list the awaits and writes between the check and the commit or the irreversible step. The check must be the last thing before it. A check that the change places, moves or leaves ahead of awaited work can pass and then be invalidated while that work runs. Put a table in your report: each such check, its line, every await or write that runs after it and before the commit, and a verdict. If anything awaited runs after the check, the verdict is a finding; the check being present is not enough, and neither is a second check elsewhere unless that one is last.

**Stored records.** A stored-record pass: for each record, file, receipt, flag, marker or row the change writes for later use, find every later step that relies on it (verify, complete, resume, repair, retry, read). Include records the change does not write but newly relies on: list every table or file that a new or changed query, view, join, trigger, verifier or repair step reads in order to decide that something is complete, current or certified, and give each one a row. When a check compares two sets, write down what each side is derived from; if both sides come from the same surviving rows, the check cannot see a row that is missing from both, and that is a finding. Ask of each: what if the record was deleted, altered, partly present, or left over from an earlier attempt? "Some rows exist" is not "all rows exist", a flag being set is not proof the work it describes is complete, and a step that never looks at the record cannot notice it is gone. When an operation is retried, resumed or re-resolved, check that it finds the same exact thing by its full identity (version, source, provenance), not just by ids that may now point at something that replaced it. Put two tables in your report. First: each stored record, each later step that should rely on it, and whether that step reads and validates it; a later step that never reads the record is a finding, not an accepted design, because it cannot tell the record is missing or wrong. Second: each retry, resume, repair or re-resolve path, the keys it matches on, and what happens if the thing under those keys was replaced, partly lost or changed kind since the first attempt.

**Summaries, digests and required sets.** When a stored or transmitted document carries both a detail and something derived from it (a list and its count, rows and a flag, content and a hash, a detailed inventory and a summary field), find where the two are reconciled. If nothing recomputes the derived value from the detail and compares them, either can be edited or go stale independently: a finding. A digest that is recorded but never recomputed, a "passed" flag accepted without the evidence, and a required set satisfied by any non-empty list are findings.

**Waiting.** A waiting pass: for each new lock, advisory lock, queue, semaphore, connection or transaction acquisition and each new network or child-process call, name what bounds the wait (a timeout, a deadline, an abort signal) and what the waiter holds while it waits (a pooled connection, a request slot, another lock). A wait with no bound is a defect, and so is a timeout with no mapped response.

**Transforms.** Check both sides of every transform. When data is transformed on its way in and compared, matched or looked up on its way out (normalisation, case folding, trimming, tokenising, encoding, hashing, rounding, unit conversion, key building), list the transform applied on the write side and on the read side, and every route by which data reaches each side: typed, pasted, imported, migrated from older rows, synced from another device, produced by a library. The two sides must apply the same transform, or both must leave it to the same engine. Trace at least these rows and state each result: stored value canonical with lookup canonical; stored value in the alternative form with lookup canonical; stored canonical with lookup in the alternative form; both in the alternative form. The alternative forms are composed against decomposed text, upper against lower case, padded against trimmed, and old-format against new-format rows. Stored values arrive in the alternative form whenever a write path skips the transform, so list the write paths that do. Do the four rows separately for each class of input that the transform or the engine treats differently. For text these are at least: plain ASCII, accented Latin letters, scripts whose characters compose and decompose (for example kana with voicing marks, Hangul syllables), compatibility forms (full-width, ligatures, superscripts), and symbols or emoji. A row that holds for one class proves nothing about another, because engines fold some classes and not others. State how many class-by-row cells you traced, and report every failing cell. A hand-written copy of what an engine or library does internally (a tokenizer, a separator list, a parser, a matcher, a collation) is a defect unless you can show it agrees with the engine on every class of input; enumerate the classes (letters, digits, marks, symbols, punctuation, whitespace, non-Latin scripts) and check each.

**Queries and ordering.** For each query the change adds or alters: a LIMIT applied before ranking, in-memory sorting or de-duplication returns the wrong subset; ordering done in the database and again in application code must agree on precision (for example microsecond against millisecond timestamps), collation and time zone, and have a stable tie-breaker; a bound, count or cap written in more than one place (SQL literal, constant, message, advertised capability) must come from one value. Put a table in your report: each query or sort, where the limit is applied relative to the final ordering, the precision and collation on each side, and the verdict.

**Limits across layers.** For each new or changed bound, type or schema: list every other layer that holds a bound for the same value (client parser, contract, server validator, database column type, audit payload, user-facing message, tests) and the actual limit at each. Any two that differ are a finding.

**Checklist.** Time: host clock against database clock; `now` read before a lock wait; zone taken from different sources in different layers; local dates derived with UTC helpers; precision mismatches; day boundaries and DST; expiry evaluated only at render; timeouts that do not compose. Migrations and stored data: applied migrations edited; missing backfill; dependent stores not remapped; `down`; old and new builds coexisting. Contracts and limits: a new bound narrower than what other layers accept; mixed client and server versions; third-party field and enum semantics.

## What to report and what not to

Report every defect you observe in the changed behavior, including small ones: rate it Low, but do not drop it. If you noticed something wrong and can state the scenario, it belongs in the findings, not in a coverage note. A stale message, a hint that outlives its truth, or an error that stays after success are defects.

Do not report style, naming, comment wording, micro-performance, or speculative "a future caller could" concerns. Defects in code the change only moved should be listed separately as pre-existing.

## Report format

For each finding:
- Title and severity (High, Medium, Low, rated by consequence).
- Invariant: the rule being broken, in one sentence.
- Sites: every violating location as `file:line`, and the sibling sites you checked and found fine.
- Scenario: concrete inputs and state leading to the wrong outcome.
- Reach: what produces the scenario's starting condition in the application as it stands today (the screen, action, caller or stored data), as `file:line`. If you find nothing that produces it today, write `no trigger found today: needs <what would have to exist>`. Keep the finding either way: this line is for whoever ranks the findings, and it is not a reason to drop or soften one.
- Fix constraint: what a correct fix must guarantee, and the inverse failure it must not create.
- Verification: reproduced, ran a test, read source, or inferred from reading.

Include every table the passes ask for.

After the tables, write a finding-row index. Give one line for every table row or cell whose verdict is `finding`: the table, the row (and column), the number of the written finding that covers it, and a quotation of the sentence in that finding that says what goes wrong at that row's own reader, site or input. A written finding about a different reader, site or path of the same value does not cover the row, even when the cause is shared. If you cannot quote such a sentence, write a new finding for the row before you finish. State the number of `finding` rows and cells in your tables and the number of index lines; the two must be equal.

End with a coverage statement: the unit ledger, the passes you ran and what you enumerated for each, anything you ran, and what you did not check and why. Then the "Outside my focus" list.
